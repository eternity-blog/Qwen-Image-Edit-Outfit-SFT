# 同数据 LoRA v2 vs 全参 SFT 训练对照报告（2026-08-15）

> **本篇一句话：** 在同一份 11 415 条 v2 换装数据上，对 Qwen-Image-Edit-2511 的 20.43B DiT 做了两种训练——**全参 SFT（ZeRO-3）**与**DiT-LoRA r16（DDP）**——除了「训练方式」本身决定的差异外，数据/步数/卡数/分辨率/精度全部对齐，构成一组干净 A/B。本文按面试问答组织，所有数字取自 safetensors header / TensorBoard 事件文件 / nvidia-smi / training_args.json，非估算。
>
> **状态：** 全参 SFT 已跑完（2h22m）；LoRA v2 **训练 + fuse 均已完成**（训练 1h49m23s + fuse 1m27s，2026-08-16 01:41 收尾）。本文所有数字为最终值。

---

## 0. 为什么有这组对照

仓库早先那版 LoRA（`train_idm_lora_multigpu.sh`）训的是 **v1 metadata**（2 条英文短指令，76–223 字符），而全参 SFT 用的是 **v2**（1 条 1592 字符中文全文模板）。评测统一用 live v2 prompt（留出集 1592、case02 2000/1922 字符），等于只把 LoRA 放到了它训练分布之外。所以那组数据**无法回答「LoRA vs 全参」**——它只能说明「指令分布不匹配会崩」（见 [EVAL_RESULTS_20260815.md](EVAL_RESULTS_20260815.md) 第 3 节）。

`scripts/train_lora_v2_multigpu.sh` 把数据固定成与全参**完全相同的 v2**，只留「训练方式」一个变量。这就是本篇对照存在的意义。

## 1. 对照设计：什么对齐、什么必然不同

### 1.1 保持一致（控制变量）

| 维度 | 值 | 来源 |
|---|---|---|
| metadata / dataset_base | `converted_idm_synth_train_v2`（同一批文件） | training_args.json |
| 训练样本 | **11 415** 条换装 pair | metadata_train.json |
| epoch / dataset_repeat | 1 / 1 | training_args.json |
| max_pixels | 1 048 576（≤1024×1024，面积上限 1MP） | 同上 |
| gradient checkpointing | 开 | 同上 |
| `zero_cond_t` | 开（Edit-2511 强制） | 同上 |
| 精度 | bf16 | 同上 |
| weight_decay | 0.01 | 同上 |
| grad_accum | 1 | 同上 |
| `find_unused_parameters` | True | 同上 |
| **NUM_PROCESSES** | **8（8×H100）** → 有效 batch 8 | launch log |
| **optimizer 步数** | **同为 1427**（⌈11415/8⌉，sampler 不 drop_last、向上 pad 到 8 的倍数） | TB 事件数 |

### 1.2 必然不同（方法本身决定，结论里必须注明）

| | **LoRA v2** | **全参 SFT** |
|---|---|---|
| 可训参数 | DiT LoRA **r16 ≈ 0.118B**（插在 13 个线性/MLP/mod 层） | **全部 DiT 20.43B**（TE 8.29B / VAE 0.13B 冻结） |
| 学习率 | **1e-4**（LoRA 惯例，大 LR） | **1e-5**（全参惯例，小 LR） |
| 分布式策略 | **DDP**（每卡复制冻结底座） | **DeepSpeed ZeRO-3**（参数/梯度/优化器三件全分片） |
| 优化器状态量 | ~1.6 GB/卡（只为 118M 付 AdamW m+v） | ~30.7 GB/卡（为 20B 付 fp32 master + m + v，已分片） |
| 初始化 | 底座 `MODEL_DIR`（从 base 起训，已确认） | 底座 `MODEL_DIR` |

> **关键点：** 两者的 LR 差 10×，这不是 bug，是方法本身的约定——LoRA 只更新低秩增量 `BA`，需要更大步长才能让增量起作用；全参直接动 20B 原始权重，1e-5 才安全。因此「loss 下降速度」不能直接跨方法比较绝对值，只能比「各自是否收敛」和「最终评测」。

### 1.3 LR 调度器（两者相同，且不绑定 epoch）

DiffSynth 训练循环 `diffsynth/diffusion/runner.py:66` 写死：

```python
scheduler = torch.optim.lr_scheduler.ConstantLR(optimizer)
```

- **不是** cosine / linear decay，**也不依赖 `num_epochs`**。默认 `factor≈1/3`、`total_iters=5`，即前 5 步半速热身、之后恒定在设定 LR。
- 含义：想把任一方法从 1 epoch 拉到 2 epoch，是「干净的平坦 LR 延伸」，没有「schedule 为 1 epoch 设计、拉长会错」的副作用。这一点直接回答了「跑两个 epoch 会不会更好」的调度层顾虑——调度层无障碍，问题只在数据/过拟合（见第 9 节）。

## 5. 显存占用分析（面试主菜）

### 5.1 两种策略的显存经济学

**LoRA DDP（每卡）：**
```text
冻结底座 bf16（DiT 40.9 + TE 15.5 + VAE 0.3）  ≈ 56.7 GiB   ← 大头：整模复制
LoRA 参数 + fp32 grad + AdamW m+v（118M）      ≈ 1.6 GiB    ← 极小
+ GC 后激活                                     ≈ ~10 GiB
峰值                                            ≈ 68 GiB / 80GB
```
**全参 SFT ZeRO-3（每卡，三者都 /8 分片）：**
```text
DiT 参数 bf16   40.9 GiB / 8                   ≈ 5.1 GiB
DiT 梯度 bf16   40.9 GiB / 8                   ≈ 5.1 GiB
fp32 master + AdamW m+v（3×20.43B×4B）/ 8      ≈ 30.7 GiB   ← 大头：sharded 优化器
+ GC 后激活 + ZeRO-3 逐层 all-gather 瞬态       ≈ ~34 GiB
峰值                                            ≈ 74.8 GiB / 80GB
```
（分解为量级说明，非逐字节精确；与实测稳态 74.4 / 峰值 74.8 吻合。）

### 5.2 反直觉点：全参 ZeRO-3 峰值反而高于 LoRA DDP

| | LoRA DDP | 全参 ZeRO-3 |
|---|---|---|
| 稳态显存/卡 | **~68.4 GiB** | **~74.4 GiB** |
| 峰值/卡 | ~68.9 GiB | **74.8 GiB（91.7%）** |
| 余量/卡 | ~12 GiB | ~5.2 GiB |

直觉可能以为「全参要省显存才用 ZeRO-3」，**反过来**：在这台 8×80GB 上，全参 ZeRO-3 峰值比 LoRA DDP 还高 ~6.8 GiB。因为：

- LoRA 的 DDP 虽每卡复制整模（56.7 GiB），但只为 118M 付优化器（1.6 GiB），净占用低；
- 全参 ZeRO-3 虽把 20B 参数/梯度各砍到 5.1 GiB，但 **fp32 master + AdamW m/v 即便分片后仍达 30.7 GiB/卡**，再加上 ZeRO-3 逐层 all-gather 瞬态与更大的激活重算，合计反超。

### 5.3 但 ZeRO-3 是「让全参成为可能」，不是「更省」

关键不是哪个更省，而是**可行性边界**：

- 若用**纯 DDP 跑全参**：每卡要放完整 optimizer state = fp32 master + m + v ≈ **245 GiB** → **必 OOM**（CLAUDE.md 硬性规定「全参 DiT 禁止纯 DDP、必须 ZeRO」的根因）。
- ZeRO-3 把这 245 GiB 切到 8 卡 → 30.7 GiB/卡，才塞进 80GB。
- LoRA DDP 之所以能用 DDP，是因为它**不为 20B 付优化器**（只付 118M），所以「每卡复制整模 56.7 GiB」反而比「每卡分片优化器 30.7 + 分片参数 5.1 + 分片梯度 5.1 + 激活」更便宜。

一句话：**LoRA = 便宜但只能改低秩增量；ZeRO-3 = 贵但能改全部 20B。两者不是「谁省」，是「改多少」的能力差。**

### 5.4 ZeRO-3 分片均匀的佐证

8 卡稳态显存均值 max−min 仅 **685 MiB（~0.9%）**，且 util 均值 92.4–97.1% 全程高位——ZeRO-3 把 params/grads/optimizer 三件套均匀切了 8 份，没有倾斜。LoRA DDP 同样均衡（max−min 588 MiB），因为每卡都是同一份冻结底座 + 同结构 LoRA。

### 5.5 为什么 LoRA 余量更大却仍走 DDP 不走 ZeRO

LoRA DDP 余量 ~12 GiB，理论上还能再塞。但没必要：可训参数只有 118M，DDP 的梯度 all-reduce 只传 118M（~0.47 GiB bf16），通信极轻；而 ZeRO-3 的逐层 all-gather 反而引入额外通信与重算，对 LoRA 是净负。所以 **LoRA 配 DDP、全参配 ZeRO-3 是各自的最优策略**，不是凑合。

## 7. Loss 分析与「能不能下结论」

### 7.1 全参：学到了，但 loss 本就低、降得慢

SFT 是在已重度预训练的 Edit-2511 上微调，模型已近最优，loss 量级本就小（去噪 MSE 在 well-trained 区间）。末 100 步比首 100 步降 23.7% 是「缓降」，不是「收敛陡降」。

### 7.2 为什么不能读单步 loss（必考）

扩散训练每步随机采样 timestep t、噪声 ε、不同图像对：
- 低噪声 t / 易样本 → loss 可逼近 0（step76 的 0.0 即此，数值下溢，**非 bug**）；
- 高噪声 t / 难样本 → loss 偏大（step6 的 0.165）。

末 100 步单步 stdev=0.0249、极差=0.1034，**噪声 ≫ 趋势**。所以：
- 不能凭单步判收敛，必须看窗口均值；
- **LoRA step1=0.01242 vs 全参 step1=0.02901 不代表 LoRA 更好**——只是不同随机 batch/timestep。

### 7.3 训练 loss 都不能下最终结论

1 epoch / 11.4k 是轻量 pass；两种方法的 train loss 都只说明「在该分布上缓缓学习」。**真正结论只能靠 held-out 评测**（见第 8 节）。

## 9. 「跑两个 epoch 会更好吗」——调度/loss/风险三层

1. **调度层：2 epoch 是干净延伸，无副作用。** ConstantLR 不绑定 num_epochs（见 1.3），2 epoch = 再追加 1427 步平坦 1e-5/1e-4。
2. **loss 层：已近平台，边际收益很小。** 全参末 4 个窗口 0.0318→0.0314→…→0.0311 基本平了，单步噪声远大于趋势。第 2 epoch 大概率原地踏步。
3. **风险层：2 epoch 更可能 hurt。** 参数/数据比极端（20B / 11.4k ≈ 1.8M 参数/样本），第 2 遍把同一批唯一图再喂一次，显著抬高 memorization 风险（train loss 继续降、生成质量开始崩）。而当前无 val 评测，单看 train loss 判不了过拟合膝点。

**结论：瓶颈是数据量/多样性，不是 epoch。加新 pair（DressCode 多类目 + 真实帧 GPT teacher，目标 35–58k）比加 epoch 更值得。**

## 10. 面试可能被问到的（速答）

| Q | A |
|---|---|
| 全参 DiT 为什么不能用纯 DDP？ | 20B 的 fp32 optimizer state ≈ 245 GiB/卡，DDP 每卡一份完整副本 → 必 OOM。ZeRO-3 把 params/grads/optimizer 全分片到 8 卡才塞进 80GB。 |
| ZeRO-3 vs ZeRO-2 区别？ | ZeRO-2 分片 optimizer+梯度，参数仍每卡一份；ZeRO-3 再把参数分片，前向/反向按层 all-gather。20B 级必须 ZeRO-3，ZeRO-2 参数不分片仍放不下。 |
| 为什么 LoRA 反而用 DDP 不用 ZeRO-3？ | LoRA 只 118M 可训，优化器状态 ~1.6 GiB，DDP 复制冻结底座 56.7 GiB + 1.6 GiB 就够；ZeRO-3 的逐层 all-gather 对 LoRA 是净负（额外通信、无收益）。 |
| 为什么 LoRA LR 1e-4、全参 1e-5？ | LoRA 只学低秩增量 BA，需更大步长让增量起作用；全参直接动 20B 原始权重，大 LR 易毁预训练表示。10× 差是方法约定。 |
| LoRA 插在哪些层？ | DiT 的 attention 投影（to_q/k/v, add_q/k/v_proj, to_out.0, to_add_out）+ MLP/mod（img_mlp.net.2, img_mod.1, txt_mlp.net.2, txt_mod.1）。覆盖 double-stream 的图文双塔。 |
| loss 这么低正常吗？ | 正常。SFT 在已很强预训练模型上微调，去噪 MSE 本就在小量级；低 loss 不等于「学好了」，要看 held-out。 |
| 单步 loss 跳很大，过拟合了吗？ | 不是。扩散每步随机 t/ε/样本，单步 stdev 0.025 ≫ 趋势，step76 还能到 0.0（数值下溢）。看窗口均值，不看单步。 |
| 全参 ckpt 40GB 能直接加载推理吗？ | 不能。它是 DiT-only（裸 key），缺 TE/VAE/tokenizer/config，且 diffusers 要求 `transformer.*` 分片格式。必须 `apply_full_dit_ckpt.py` 嫁接回完整目录。 |
| 为什么是 1427 步？ | 11415/8=1426.875，sampler 不 drop_last、向上 pad 到 8 的倍数 → 11416 样本，每 rank 1427 步。 |
| 显存峰值 74.8GB，余量才 5GB，稳吗？ | 稳。stdev 234 MiB，8 卡均衡（max−min 685 MiB），全程无 OOM；峰值是 ZeRO-3 all-gather 瞬态 + 激活重算叠加的稳态高点，不是泄漏增长。 |
| LoRA DDP 68GB、全参 ZeRO-3 74.8GB，为什么全参更高？ | LoRA 不为 20B 付优化器（只付 118M 的 1.6 GiB）；全参即便分片，fp32 master+AdamW m/v 仍 30.7 GiB/卡，再加 all-gather 瞬态与更大激活，合计反超。 |
| 2 epoch 会更好吗？ | 调度层无碍（ConstantLR 不绑 epoch），但 loss 已近平台、参数/数据比极端，2 epoch 主要加 memorization 风险。瓶颈是数据（11.4k 对 20B 偏低），加新 pair > 加 epoch。 |
| 怎么判断真学到了？ | 双轨 held-out：域内 `eval_viton_holdout.py`（VITON test，有 GT）+ 业务域 `run_case02_v2_prompt_eval.sh`（真实帧 + GPT 参照）。train loss 判不了。 |
| 数据多少够？ | 20B 窄域换装 SFT 舒适区 ~20–40k 唯一多样 pair；当前 11.4k（k=1）在下沿。仓库计划 k=3→34.9k / k=5→58.2k。关键不是堆量是多样性（prompt/品类/姿态/字幕）。 |
